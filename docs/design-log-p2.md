## Growth factor and amortized cost
For the conversation class, I implemented a dynamic array which had a growth factor of 2, which meant that it doubled in size every time it had to grow. Appending to an array at full capacity, where size_ == capacity_, a new array of double the size is allocated, and the existing elements are afterwards able to be copied over before the element is appended.
	I believe that this has an amortized insertion cost of O(N) because the cost of inserting an element is the cost of the actual insertion, which is equal to one, plus the cost of copying existing elements for each resize triggered, which happens at capacities 1, 2, 4, 8, so on and so forth.
To insert N elements, the program performs N basic insertions and N- 1 copy operations. The formula for the total operation cost is 2N - 1, which has a complexity of O(N). However, the best-case complexity is O(1) for the times when there is no resizing necessary, making me somewhat unsure of the true answer.

## Rule of Five evidence
The Conversation implementation directly manages an allocated array of Message objects. To prevent memory leaks and to generally increase the quality of the code, I implemented the Rule of Five. 
	The destructor simply calls delete[] data_, ensuring any dynamically allocated memory is returned to the system when the conversation goes out of scope. The copy constructor and copy assignment perform deep copies. Instead of copying the pointer the program allocates a brand new Message array matching the capacity of the source. The program then iterates through the source elements and copy their contents into the new buffer. The move constructor and the move assignment optimize performance by taking the memory pointer from a temporary source object. After taking ownership of other.data_, the program immediately makes the source object's members zero, so other.data_ = nullptr, other.size_ = 0, and other.capacity_ = 0. This ensures the moved-from object remains in a valid, empty state and its destructor will safely call delete[] nullptr without messing up. These implementations are fairly uninteresting and are similar to the Rule Of Five implementations shown in class, except tailored for this class, of course.

## Sentinel scanner: bounded pending_ proof
The SentinelScanner is designed to detect a multicharacter sentinel string which has a length of L inside of a stream of chunked text without concatenating the entire stream into memory. 
To work at O(N) complexity for the chunks, the scanner's pending_ buffer holds a maximum of L - 1 characters at any time. The mathematics works like this: 
	L == sentinel_.size(). Before any feed operation, pending_.size() == L – 1. Then a chunk with size == C arrives, with C being the length of the chunk. The new concatenated string length is pending_ == pending_ + C . Then the program searches the new pending_ for the sentinel. If the sentinel is found, the buffer is flushed up to the sentinel, and pending_ becomes empty (L – 1). If the sentinel is not found, the program cannot rule out that the final characters of pending_ might form the beginning of a sentinel with the next chunk. And the maximum possible partial match that could overlap with the next chunk is exactly L - 1 characters. Finally, the algorithm safely emits pending_.size() - (L – 1) characters and retains only the trailing L - 1 characters in pending_. As such, at the end of the execution block, the size of pending_ is reset to L – 1. As pending_ never exceeds L - 1, the memory amount concerned relies solely on the length of the sentinel, avoiding possible memory leaks caused by unbounded string concatenation. 

## What I would change differently
For starters, I would start working on the project earlier! I would also plan more so that I can keep track of what the status is on the project at any given time. But concerning the code itself, if I were to rewrite this project, I would probably change the method of initialization in the Conversation class. Currently, the default constructor initialize capacity_ to 0 and data_ to nullptr. While this is mostly fine for completely empty conversations, it guarantees an immediate reallocation on the first append operation.
	Pre-allocating a small default capacity, such as 4 or 8, in the default constructor would be marginally better. Paying a tiny and fixed memory cost upfront would eliminate the overhead of the initial 0-to-1 and 1-to-2 capacity jumps. At the same time, I think that this is really just splitting hairs, so I would be interested to see a situation where this is critical.
	Finally, if I could change the header files, I would add a method to get capacity_ from a conversation object. This would have helped a lot for test case 7.
